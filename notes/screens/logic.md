元の Swift ソースではない。給与の 7500 円は画面で読んだ値ではない。

## 選んだ日へパターンを置く

確定。保存済みの型は `ShiftPart`（`AppData.shiftParts`）。`WeekTemplate` ではない。

日チップ `0x10003fe54` とカレンダーの行 `0x10006e04c` は、衝突配列が空のときだけ `0x100014370` を呼ぶ。衝突があるときは `PendingPlace` を `__pendingPlace` へ書く。配置 `0x1001c75ec` は次のとおり。

- `workplaceID` が無いと、日のループの前に戻る。何も置かない
- 同じ `partID` が既にある日は足さない
- `startMinute` と `endMinute` を 1440 分で正規化し、時と分に分ける。秒は 0
- `start >= end`（同じ分を含む）は終了を翌日にする
- `defaultTodos` は新しい id でコピーし、`done` は 0
- `ShiftPart.breakMinutes` は読まない。渡す `Meta.breakMinutes` は空

未確定。置いた `ShiftInstance` の Published の保存先。配置は `AppModel` のアクセサ `0x10001c974` を呼ばない。次の `0x1001d1b74` も呼ばない。`_data`、`_notice`、`_placements`、`lastPlacedAt` への書き込みは、この 2 関数には無い。

## 重なり

設定の専用関数 `0x10018dc8c` は、`0x1004ff820` の説明を読む。文は「シフトの時間が重なったときや、違う勤務先のシフトの間が移動にかかる時間より短いときに、保存の前に確認し、カレンダーと一覧に印を出します。」

確定。`0x100016734` は既存の `ShiftInstance` を走査する。日付は `bySettingHour` で作り、`0x100016d64` で二つの保存値を比べ、左が右以上なら `0x100016de8` で 1 日足す。配置関数では同じ形が `startMinute >= endMinute` だった。この関数の二つの値がそのフィールドだとまでは閉じていない。比較そのものは `Date.<` なので、日をまたいだ終了も絶対時刻として重なりに入る。

- 要素先頭の文字列が保存済みの文字列と等しければ次へ進む
- `start < 相手の終了` かつ `相手の開始 < end` なら、その場で衝突。端が同じ時刻だけの接触は、この `<` には入らない
- そうでなく、`workplaceID` が等しく、`Calendar.isDate(_:inSameDayAs:)` が真なら衝突
- そうでなく、スタック +0x280 の値を 60 倍した秒が 0 より大きいときだけ、`timeIntervalSince` の秒がその秒数未満なら衝突にする

文言を作るのは `0x1001b4e08`。カウントが cstring のバイト数と一致するアドレスを、その文言とする。`sub #0x20` の側は前の文字列の途中になる。

- 引数のバイトが 1 で、`x19` が 0 でないとき、`0x1005001b0` の「のシフトがあります」（27 バイト）
- そのバイトが 1 で `x19` が 0 のとき、先に作った文字列のあとへ `0x100500200` の「と時間が重なっています」（`0x1b + 6` = 33 バイト）
- そのバイトが 1 でないとき、`0x1005001d0` の「分しかありません（移動に」（36 バイト）

題「このシフトは確認が必要です」（39 バイト、`0x100500270`）は、`ShiftEntryEditor` だけを呼ぶ `0x1001b960c` が読む。この関数は `alert(_:isPresented:actions:message:)` を作る。

確定。保存の入口 `0x1001b9fe4` もこのアクセサだけを呼ぶ。重なり `0x100016734` の戻り配列の +0x10 が 0 なら `0x1001bf4fc` へ進む。0 でなければ、その配列を `LazyState.wrappedValue` の setter でエディタの状態へ書き、保存には進まない。ボタンを作る `0x1001bf1d4` もこのアクセサだけを呼ぶ。通常の `Button` は `0x1005002a0` の「このまま保存」（18 バイト）。`ButtonRole.cancel` のラベルは即値で「やめる」（9 バイト、`0x1001bf3b4`）。cstring ではない。繰り返し編集だけの `0x1001fc2a4` も、同じ 18 バイトと同じ「やめる」の即値でボタンを作る。

移動の分岐も、この配列に要素を足す。フラグが 1 の要素も、1 でない要素も、個数が 0 でなければ同じアラートに入る。文言の違いはフラグで、ボタンの有無はフラグで分かれていない。

移動の秒数は、この関数が x20 で受けたオブジェクトの `Published` を、key path `0x100427748` と `0x100427770` でフレーム +0x220 へ読み、その +0x60 を取る。60 を掛けた秒（`0x1000171f0` の即値 `0x3c`）が 0 以下なら、間隔の検査はしない。0 より大きいときだけ `Date.timeIntervalSince` の秒と比べ、秒数未満なら衝突にする。フラグは 0。表示する分は、その秒を 60.0（`0x100017234` の `0x404e000000000000`）で割り、0 方向へ切り捨てる。+0x60 が `travelMinutes` というフィールド名であることは、この読み出しだけでは閉じていない。設定の説明は「違う勤務先のシフトの間」と書く。命令の移動分岐は、時間の重なりでも同一勤務先の同日でもなかった項目に対する間隔の検査である。

観測。設定の「勤務先の移動にかかる時間」は分のステッパーで、このスクショでは 30 分だった。30 はこの比較の即値には無い。編集シートの保存で、題と「と時間が重なっています」、`やめる` と `このまま保存` が出た例がある。移動不足の文言が同じダイアログに出ることは、そのスクショには無い。

呼び出し。`ShiftEntryEditor` だけの `0x1001b9fe4` が、この判定を直接呼ぶ。繰り返し編集だけの `0x1001fbdc0` は `0x100017d04` を呼び、その先が同じ判定である。給与エンジン `0x10011b1d0` を直接呼ぶ関数は、画面アクセサを呼ばない。どの画面の見込みかは、この 1 段では決まらない。

## 支給の見込みと明細

確定。明細の専用関数 `0x10014e3b4` は、ある構造の +8、+0x10、+0x18、+0x20 の 4 つの倍精度を足し、別の倍精度から引く。`PayResult` の並びは base、premium、allowance、transport がこのオフセットと一致する。もう一回は、+0x28 の倍精度から同じ 4 つの和を引く。説明の cstring `0x1004fe070` は「明細 − 見込み」で、見込みの総支給額は交通費まで、差引支給額は税金と社会保険の天引きで見込みより少ない、と書く。`0x1004fdc00` は「税金・社会保険は計算していません。」アプリはこの天引きを計算しない。

観測。期間の明細は、時給 × 時間、交通費、その和を支給の見込みとして出す。総支給額と差引支給額は手入力で、未入力の保存は押せない。個人の金額は書かない。

## 給与

確定している式は `notes/HANDOFF.md` の検証済みの節。ここには画面との境界だけを繰り返す。

- 一覧カードの 1 秒タイムラインだけが、勤務中の金額を更新する経路として結んである。30 秒のスケジュール 2 箇所は別
- 表示する円は `base + premium`。手当と控除はこの和に入らない
- 休憩の按分は予定の start/end を変えず、`breakMinutes` だけを書き換える
- 丸めは startOfDay からの秒で、1440 分では巻かない
- 時給履歴は末尾から、`effectiveFrom` がシフト日以下の最初の `hourlyWage`。空なら 0
- 交通は、対象の kind で amount が 1 以上なら一度足す

未確定。日給の二つの UUID のフィールド名。perDay の回数。手当と控除の加算。ゲート日付が `now` そのものか。履歴が日付順か。全部がシフト日より後のときの戻り。年収の壁の閾値。
